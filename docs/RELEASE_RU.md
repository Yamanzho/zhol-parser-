# Жол 0.2.0: локальная установка и миграция

Это локальный кандидат. Публичный выпуск на GitHub не создаётся. Рабочая база этой проверкой не изменялась.

## Что входит

- Поиск компании идёт по ключам, а не по всем компаниям города.
- Сомнительный кандидат не присоединяется молча.
- CSV и JSON пишутся порциями. Прежний предел в 5 000 строк снят.
- Excel по-прежнему вмещает не больше 1 048 575 строк данных. Для большего объёма выберите CSV или JSON.
- Команда `python -m zhol.cli rebuild-match-keys` заново строит ключи и не меняет компании.
- Команда `python -m zhol.cli identity-report` только печатает неподтверждённые пары снимков. Она работает в транзакции только для чтения и больше не падает с ImportError при запуске в новом процессе.
- Команда `python -m zhol.cli schema-check` сравнивает ревизию базы с программой и ничего не меняет.
- «Запустить Zhol.command» больше не обновляет базу с данными. Он проверяет схему до запуска служб и останавливается, если она не совпадает.
- Новая команда «Обновить базу Zhol.command» (`scripts/zhol-upgrade-db.sh`) обновляет базу явно.
- Сборщик macOS не стартует на несовпадающей схеме и ждёт обновления.
- Резервные копии делаются и после сна Mac, файлы закрыты для других пользователей и не перезаписываются. Подробности: `docs/ops/postgres-backup.md`.

Версия пакета, приложения FastAPI и панели: `0.2.0`. Пути API остаются `/api/v1`.

## Установка

На компьютере, где Жол уже стоит в `.venv`:

```bash
python -m pip install -e ".[dev]"
```

Демонстрация без базы собирается заново так:

```bash
scripts/build-macos-demo.sh
```

Готовое приложение не открывает PostgreSQL и не ходит на карты.

## Проверка схемы при запуске

«Запустить Zhol.command» собирает образ и до запуска API, панели, воркеров и резервного копирования выполняет `python -m zhol.cli schema-check`:

| Код | Что значит | Что делает запуск |
|---|---|---|
| 0 | схема совпадает | запускает службы, миграций нет |
| 3 | база старее программы | останавливается и предлагает «Обновить базу Zhol.command» |
| 5 | база новее программы, ревизия неизвестна или отметки нет | останавливается, нужна проверка человеком |
| 4 | база пустая, новая установка | создаёт таблицы и запускает службы |
| 2 | базу не удалось прочитать | останавливается |

При остановке уже работающие службы не трогаются, данные не меняются. Сборщик macOS при старте делает ту же проверку и при несовпадении выходит, не начиная сбор. После обновления базы его включают снова: `scripts/zhol-collector-macos.sh start`.

## Миграция установленного Жол

1. Обновите программу до 0.2.0 (`git` или новый архив). Службы при этом не перезапускаются.
2. Дважды щелкните «Обновить базу Zhol.command» и наберите `ОБНОВИТЬ`.
3. Команда сама:
   - собирает образ;
   - проверяет ревизию;
   - останавливает сборщик macOS этого каталога, API, панель, воркеры и резервное копирование;
   - ждёт, пока к базе не останется подключений, и при чужом подключении останавливается без миграции;
   - пишет копию в `data/backups/pre-upgrade/` (права `400`, рядом `.sha256`) и проверяет её `pg_restore --list`;
   - выполняет `alembic upgrade head` и снова проверяет схему.
4. Запустите «Запустить Zhol.command».
5. Включите сборщик: `scripts/zhol-collector-macos.sh start`.
6. Проверьте: `python -m zhol.cli identity-report`.

Если база уже совпадает, команда пишет «Обновление не нужно» и ничего не останавливает. На неизвестной ревизии она тоже ничего не останавливает.

Для разработки без Docker, с остановленными API и сборщиками и с адресом базы в `DATABASE_URL`:

```bash
alembic upgrade b6d2f4a81c30
```

Миграция добавляет таблицу `company_match_keys` и индексы. Существующие компании, снимки и идентификаторы площадок она не переписывает. Ключи заполняются из текущего имени компании и из телефонов последнего снимка каждой площадки.

Если компании когда-либо записывались прямым SQL в обход приложения, после наката выполните:

```bash
python -m zhol.cli rebuild-match-keys
```

Повторять команду безопасно. Запустите API только после успешного наката.

Проверка без изменения строк:

```bash
python -m zhol.cli identity-report
```

## Откат

Откат схемы выполняет код 0.2.0: в 0.1.0 нет описания этой миграции.

1. Остановите всех, кто пишет: `scripts/zhol-collector-macos.sh stop`, затем `docker compose -f docker-compose.yml -f docker-compose.offline.yml --profile backup stop api web worker browser-worker backup`.
2. Пока стоит 0.2.0:

```bash
docker compose -f docker-compose.yml -f docker-compose.offline.yml run --rm --no-deps -T api alembic downgrade e5a9b3c20f41
```

3. Верните программу 0.1.0 и запустите её как обычно.

Второй путь: восстановить копию из `data/backups/pre-upgrade/` по `docs/ops/postgres-backup.md`. Записи, сделанные после обновления, при этом пропадут.

Откат удаляет ключи и индексы этой миграции. Строки компаний, снимков и идентификаторов площадок остаются. После отката поиск компании снова читает город целиком, как до `0.2.0`.

Если накат оборвался, PostgreSQL откатывает всю миграцию целиком: таблица ключей не остаётся наполовину созданной. Повторите «Обновить базу Zhol.command».

## Прямой SQL

Обычные записи приложения сами обновляют ключи. Прямой `INSERT` и `UPDATE` в `companies` или `card_snapshots`, а также пакетная вставка мимо ORM, ключи не обновляют. Пока не выполнена пересборка, повторный импорт той же компании может создать вторую запись. Это поддерживаемый обходной путь только вместе с `rebuild-match-keys`.
