# S3. API, Syntony, счёт и оплата, админка для решений человека

**Зависит от:** S0. Можно вести параллельно с S1-S2.

## Цель

Бек в Syntony создаёт заказы, выставляет счета, передаёт материалы и решения клиента; Жол узнаёт об оплате и отказах.
Пока Syntony не подключён, всё работает в режиме `stub` (журнал и Telegram), а оплату может подтвердить человек в админке.
Минимальная админка нужна уже здесь: через неё человек решает задачи «нужен человек» и проверяет первые работы.

## Входы

- ТЗ разделы 6, 9; `01` разделы 3 (`deals`, `orders`, `invoices`, `credentials`, `events_out`), 4.2-4.3, 9-12
- `source/duna-agent-integration-notes-v1.md` (поля и инструменты, которые ждёт Бек; тесты 3-7 раздела «Проверки перед продом»)
- `source/duna-agent-system-prompt-v1.md` (этапы сделки, правила оплаты и доступов)

## Скиллы

`zhol-stage`, `/security-review` (API, вебхуки, хранилище доступов, админка), `verification-before-completion`, `/code-review`, `zhol-acceptance`.

## Шаги

1. FastAPI: все пути `01` раздел 10. `X-Api-Key`, вебхуки с проверкой подписи. Ответы для Бека с `order_id` и подписями для клиента.
2. `POST /api/v1/companies`: ссылка 2ГИС → id → компания (`source=inbound`) → `scout.collect(prospect)`.
3. `POST /api/v1/orders`: `deal` + `order` (`created`), сумма по прайсу из ТЗ раздел 4 (код, `config/pricing.yaml`).
   Больше 3 филиалов: заказ не создаётся, ответ «передать человеку» и `human_task`.
4. `POST /api/v1/orders/{id}/invoices` → `invoice.issue` → `InvoiceProvider` (`stub` и интерфейс `syntony`), ключ идемпотентности = заказ + часть.
   В `stub` человек выставляет счёт в Kaspi и закрывает задачу в админке, указав номер счёта: счёт `issued`, заказ `prepay_invoiced`.
   `kind=subscription` без закрытого разового заказа в сделке: отказ «передать человеку» (N28).
5. Три пути отметки оплаты (`01` раздел 9): вебхук `payment.paid`, `check()`, подтверждение человека в админке (роль `owner`, комментарий обязателен).
   Других путей в коде нет (тест N6).
6. Вебхуки `dnc.set`, `deal.lost`. `events_out` с повтором и режимом `stub`.
7. `POST /api/v1/credentials`: шифрование `SECRETS_KEY` (Fernet), в ответе только `credential_id`. Пароль не попадает в логи, ответы, `human_tasks`, `llm_calls`.
   Расшифровка только в команде `browser-login` (`01` раздел 12), её делает S5.
8. Подписанные ссылки на файлы `/files/{token}` (`01` раздел 11).
9. Минимальная админка (FastAPI + шаблоны): вход по логину и паролю (хэш), роли `owner` и `operator`, только HTTPS.
   Экраны: очередь `human_tasks` с решением и комментарием; закрытие задачи «выставить счёт» с номером счёта Kaspi;
   решение по вердикту `human` консилиума (кнопки «пропустить / вернуть автору / отменить», `03` шаг 6а);
   проверка «первых N» (`human_first`, блокирующая) с кнопками «да / нет» и полем «что пропущено» (пишется в `review_quality`);
   экран «казахские тексты» для носителя языка (решение Р8); подтверждение оплаты; журнал событий в Syntony.
10. Перенос решений `human-review` из CSV (S2) в админку.
11. `docs/syntony-contract.md`: каждый путь и событие с примером запроса и ответа. Тимур передаёт разработчикам Syntony.
12. Тесты: контрактные на каждый путь, подписи, идемпотентность, переходы заказа, тесты 3-7 из `duna-agent-integration-notes-v1.md` в части Жола.

```text
Этап S3 сервиса «Жол». Прочитай AGENTS.md (6, 9), docs/plan/01-arkhitektura.md (3, 4.2-4.3, 9-12), docs/plan/stages/S3.md,
source/duna-agent-integration-notes-v1.md. Используй zhol-stage; в конце /security-review.

Задача: API для агента Бека, вебхуки Syntony, заказ, счёт и оплата, хранилище доступов, подписанные ссылки, минимальная админка.

Жёсткие правила:
- Сумму счёта считает код по прайсу. Ни Бек, ни модель сумму не задают.
- Оплата отмечается только тремя путями из 01-arkhitektura.md раздел 9. Напиши тест, который доказывает, что других нет.
- Заказ не переходит дальше prepay_invoiced без оплаты (transition из S0).
- Пароли клиентов только шифром. После тестов поиск тестового пароля по логам должен давать 0 совпадений.
- Режим stub по умолчанию: счёт = human_task, события = журнал + Telegram.

Сначала покажи docs/syntony-contract.md, после «ок» пиши код. В конце /security-review, zhol-acceptance S3, council-dev --stage S3.
```

## Приёмка

| # | Проверка | Ожидаемо |
|---|---|---|
| 1 | Вебхук без подписи или с неверной | 401, ничего не изменилось (N5) |
| 2 | Цепочка заказа в режиме stub | `POST /orders` → `POST /invoices` (human_task «выставить счёт» в Telegram) → закрытие задачи с номером счёта (`prepay_invoiced`) → подтверждение оплаты в админке → заказ `intake`, событие `intake_missing` |
| 3 | Та же цепочка с тестовым вебхуком `payment.paid` | Заказ `intake` |
| 4 | Работа без оплаты (API и прямой вызов) | Отказ (N7) |
| 5 | Двойной счёт с одним ключом | Один счёт (N8) |
| 6 | Пароль клиента | В базе шифр; поиск тестового пароля по логам, ответам и таблицам: 0 |
| 7 | `dnc.set` | Компания не в экспорте, события по ней не уходят (N2) |
| 8 | Больше 3 филиалов; подписка без закрытого разового заказа | Заказ не создан, `human_task` (N26, N28) |
| 9 | Админка без входа | Недоступна; оператор не может подтвердить оплату, владелец может |
| 10 | `docs/syntony-contract.md` | Передан в Syntony; вопросы разработчиков Syntony закрыты или записаны в `docs/backlog.md` |
| 11 | `/security-review` | Нет замечаний high и medium |

**Тимуру проверить руками (20 минут):** войти в админку, пройти цепочку п. 2 на тестовом заказе, подтвердить оплату, увидеть сообщения в Telegram.
