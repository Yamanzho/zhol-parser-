# S4. Материалы клиента, пакет правок, ответы на отзывы

**Зависит от:** S2, S3.

## Цель

После оплаты собрать у клиента материалы, разобрать их в данные бизнеса двумя независимыми чтениями, собрать пакет правок
по трём площадкам, ответы на отзывы и жалобы, пропустить через консилиум и получить утверждение клиента.

## Входы

- ТЗ разделы 4, 5.4 (часть 1), 5.7 (чек-лист), 9; `01` разделы 3 (`company_profiles`, `client_messages`, `client_files`, `change_packages`,
  `change_items`, `reviews`), 4.2, 5, 10; `03` раздел 3.1, строки 5-9 и 15; `04` разделы 2-3
- Промты `intake-extract`, `executor-package`, `executor-review-reply`, `executor-complaint`, `executor-fix-reply`
- Чек-листы `package`, `review_reply`, `kazakh_text`
- `config/platforms.yaml`, раздел `editable_fields`: какие поля можно править на каждой площадке и их ограничения.
  В S4 Ербол делает черновик по официальной справке площадок (ссылка и дата). В S5 черновик сверяется с кабинетами AOE,
  отличия записываются в `docs/decisions.md`

## Скиллы

`zhol-stage`, `zhol-prompt` (четыре промта, золотые наборы), `zhol-council` (точки `intake_double_read`, `package`, `review_reply_*`,
`complaint`, надбавка `kazakh_text`), `/security-review` (загрузка файлов), `verification-before-completion`, `/code-review`, `zhol-acceptance`.

## Шаги

1. Чек-лист приёмки (ТЗ 5.7) в `intake.checklist` при переходе заказа в `intake`. Пункты доступов к карточкам не держат переход `intake → package`:
   их проверяет только переход в `applying` (S5).
2. `POST /materials`: сообщения в `client_messages` (`id` = id сообщения Syntony), файлы в `client_files` (тип по содержимому, лимит 50 МБ).
3. `intake.parse`, точка `intake_double_read`: Claude и GPT независимо выполняют `intake-extract`. Код сравнивает услуги, цены, график, адрес, телефоны.
   Совпало: в `company_profiles` (новая версия). Не совпало или `needs_confirmation`: вопрос клиенту через событие `intake_missing`.
4. `intake.check`: чего не хватает → `intake_missing` со списком простыми словами. Материалы закрыты и заказ в `intake` → переход в `package` и `order.prepare_package`.
5. `order.prepare_package` ставит `scout.collect(order_fresh)` и `reviews.collect` (публичные страницы: отзывы за 30 дней без ответа в `reviews` с `order_id`).
   Готовность проверяет идемпотентная задача `order.check_package_ready` (`01` раздел 5): её ставят и сбор, и итог проверки каждого ответа.
   Отзывов 0: готово сразу. Ответ с итогом `human` в пакет не входит. Всё готово: `executor.package`.
6. `executor.package`: промт `executor-package` → новая версия `change_packages` (старая `superseded`). Код добавляет проверенные ответы на отзывы 4-5
   пунктами с полем `review_reply` (`after` = текст, `source_ref` = `review:<id>`), с общей нумерацией `n`: клиент может исключить ответ так же, как правку.
   Код: `is_nap` по полю, `counts_to_limit = false` (разовая работа), `n` по порядку, `idempotency_key`, поле есть в `editable_fields` (кроме `review_reply`, который добавляет сам код),
   `source_ref` указывает на существующее сообщение, файл или поле профиля, цены и услуги совпадают с профилем символ в символ,
   фото только `photo_real` или готовый контент. Нарушение: правка отбрасывается и записывается в журнал.
7. Нужный контент (`content_needed`): записи `content_items`. До S6 пакет идёт без них, с пометкой «контент будет добавлен».
8. На каждый отзыв `executor.review_reply`. Код ставит согласование: оценка 3 и ниже или флаг модели. Точка `review_reply_positive` или `review_reply_negative`.
   Для оценок 3 и ниже `executor.complaint`, точка `complaint` (двойное решение): жалоба только если оба сказали «да»; тогда она идёт клиенту через `/approvals`.
9. `review.run(point=package)`: консилиум; возврат через `executor-fix-reply`; до 3 кругов; первые 10 пакетов после `pass` ждут «да» Тимура в админке, только потом уходят клиенту.
   Текст на казахском: надбавка `kazakh_text`.
10. Пакет для клиента: пронумерованные правки с подписями «площадка, что меняем, было, станет», картинка «было и станет», `summary_for_client`.
    Событие `package_ready`. Ответы на отзывы 3 и ниже и жалобы: событие `review_approval_needed`, решения через `/approvals`;
    одобренное ставит `executor.apply` (S5) только для площадок с `access_status = verified`; остальное ждёт проверки доступа. Пока носитель казахского не назначен (Р8), ответы на казахском тоже идут через `/approvals`.
11. `POST /package/approval`: `all`, `approve_except`, `approve_only`, отдельно `nap_consent`. Правки названия, адреса, телефона, рубрики без
    согласия остаются `waiting_nap_consent` и не держат заказ; позднее согласие сразу ставит `executor.apply` только для них (`01` раздел 4.2).
    `POST /package/rework`: новая версия пакета по просьбе клиента.
12. Контент, готовый после отправки пакета клиенту: новая версия только с новыми пунктами, отдельно на утверждение.

```text
Жёсткие правила (код в guards.py + тест на каждое, это негативные тесты N9-N13):
- Правка без существующего source_ref отбрасывается.
- Цена или услуга не совпадает с профилем клиента: отбрасывается.

- Фото только photo_real или готовый контент cover/promo_banner/price_image.
- Ответ на отзыв 3 и ниже или с флагом модели не публикуется без согласия клиента.

Золотые наборы: 3 вымышленных салона (прайс текстом, прайс фото, неполные данные) для intake-extract и executor-package;
tests/golden/package/ 10 верных пакетов и 5 с ошибками (выдуманная цена, услуга без источника, смена названия без пометки,
сгенерированное фото, обещание в summary); tests/golden/review_reply/ 10 и 5. Покажи eval, потом API.
В конце /security-review, zhol-acceptance S4, council-dev --stage S4.
```

## Приёмка

| # | Проверка | Ожидаемо |
|---|---|---|
| 1 | Неполные материалы | Клиенту уходит список ровно того, чего не хватает |
| 2 | Фото прайса с размытой ценой | Двойное чтение расходится → вопрос клиенту, в профиль не попадает |
| 3 | Подложенные правки: без источника, с ценой не из профиля, с фото не от клиента | Все три отброшены кодом (N9, N10, N12) |
| 4 | Смена названия без согласия | `waiting_nap_consent`, заказ идёт дальше без неё (N11) |
| 5 | Отзыв 2 звезды | Ответ ждёт `/approvals` (N13) |
| 6 | Жалоба: одна модель «да», другая «нет» | Жалоба не подаётся |
| 7 | Консилиум пакета | `eval --point package`: 10 из 10 верных проходят, 5 из 5 ошибок пойманы |
| 8 | Пакет для клиента | Тимур читает 3 пакета: по каждой правке понятно, где, что было и что станет; ни одного внутреннего термина |
| 9 | Частичное утверждение «всё, кроме 2 и 5» | Ровно эти две правки `rejected_by_client` |
| 10 | `/security-review` загрузки файлов | Нет high и medium |

**Тимуру проверить руками (30 минут):** 3 пакета из п. 8 и первые пакеты в админке.
