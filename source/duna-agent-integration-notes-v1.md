# Интеграция агента Duna.kz в Syntony

Этот документ предназначен для разработчиков CRM Syntony. Он описывает, как подключить tenant-specific промт Duna.kz так, чтобы общий агент «Тех. поддержка» и остальные тенанты не изменились.

## Что нужно сделать

1. Проверить в коде `agentflow`, какое tenant-specific поле действительно имеет приоритет и подставляется вместо общего шаблонного промта: `SystemPromptOverride` или `UnifiedPrompt`.
2. Записать содержимое файла `duna-agent-system-prompt-v1.md` в рабочее поле только для тенанта Duna.kz:
   - tenant id: `c3cd831f-b753-4acb-bf6a-9002e0ffa289`;
   - slug: `dunakz`.
3. Не изменять шаблонный агент `5e2dec01-…-000000000007` и его версию v4, потому что этот агент используется другими тенантами.
4. Убедиться, что tenant override заменяет таксопарковый промт, а не добавляется после него. В итоговом system prompt Duna.kz не должно оставаться инструкций про водителей, курьеров, комиссии, выплаты, блокировки, забытые вещи и «Байгу».
5. Сохранить резервную копию текущей записи `AgentTenantConfigs` перед изменением.
6. После записи прочитать фактически собранный prompt из runtime `agentflow` и проверить, что применяется версия Duna.kz.

## Что передавать в runtime

Для каждого сообщения желательно формировать структурированный контекст:

```json
{
  "tenant_id": "c3cd831f-b753-4acb-bf6a-9002e0ffa289",
  "conversation_direction": "inbound | outbound",
  "lead_id": "...",
  "company_name": "...",
  "contact_name": "...",
  "contact_role": "...",
  "city": "...",
  "industry": "...",
  "branch_count": 1,
  "lead_source": "...",
  "pipeline_status": "...",
  "audit": {
    "completed": true,
    "observations": [],
    "evidence_urls": []
  },
  "dnc": false,
  "last_contact_at": "...",
  "next_contact_at": "...",
  "invoice_status": "none | issued | paid | failed",
  "payment_status": "unverified | paid | failed",
  "materials_status": "...",
  "access_status": "...",
  "work_status": "..."
}
```

Критично передавать `conversation_direction`, `pipeline_status`, `audit.observations`, `dnc` и результаты финансовых инструментов. Без них агент не сможет безопасно отличить входящий запрос от исходящей продажи, персонализировать первое сообщение и подтвердить оплату.

## Необходимые инструменты

Агенту нужны инструменты с однозначным успешным или ошибочным результатом:

- чтение и обновление CRM-лида;
- установка DNC;
- создание задачи сотруднику;
- handoff оператору;
- выставление удалённого счёта Kaspi;
- проверка фактического поступления оплаты;
- безопасное сохранение учётных данных в отдельном credential-поле;
- получение результата аудита карточек;
- фиксация отправки изменений на модерацию;
- отправка итогового отчёта.

Если какого-либо инструмента нет, его действие нельзя имитировать текстом. Временная безопасная логика - создать задачу сотруднику и не утверждать клиенту, что операция выполнена.

## Настройки агента

Рекомендуется:

- оставить температуру около `0.3`;
- включить validator или output checker хотя бы для цен, гарантий, статуса оплаты и DNC;
- включить handoff либо реализовать обязательную CRM-задачу `needs_human`;
- хранить версию промта и дату развёртывания;
- логировать выбранный режим `inbound/outbound`, стадию и вызванные инструменты;
- запретить отправку исходящего сообщения без подтверждённого аудита и при `dnc=true` на уровне кода, а не только промта;
- ограничить исходящие сообщения рабочим временем по часовому поясу контакта.

## База знаний

После успешного включения tenant-specific промта:

- файлы 01-14 оставить как справочную базу продукта;
- правила поведения, продажи, квалификации, возражений и follow-up держать в system prompt;
- файлы 15-20 можно удалить из RAG или оставить только как резерв, но они не должны считаться основным механизмом управления поведением;
- при конфликте RAG-фрагмента с system prompt всегда должен побеждать system prompt;
- retrieval должен возвращать факты продукта, а не случайные инструкции поведения.

## Реестр регалий и рекламных утверждений

Передавать в prompt или базу знаний только утверждения со статусом `approved`. Для каждой регалии желательно хранить:

- точную разрешённую формулировку;
- критерий и единицу измерения;
- источник;
- дату проверки;
- дату следующего пересмотра;
- область применения;
- запрещённые расширительные трактовки.

На дату подготовки промта разрешены: работа Duna.kz с 2014 года; позиционирование маркетингового агентства в Казахстане; собственная исследовательская практика Kazakhstan Data Hub; более 100 исследований и более 6 000 показателей; исследования спроса, поисковой выдачи и экономики привлечения более чем в 100 нишах.

Не разрешено без отдельного сравнительного исследования: «самое большое исследовательское агентство Казахстана», «крупнейшее», «№1» или «лидер рынка». Количество материалов в Data Hub само по себе не доказывает размер агентства, выручку, штат, долю рынка или лидерство среди специализированных исследовательских компаний.

## Проверки перед продом

Провести минимум следующие тесты:

1. Входящий запрос «Сколько стоит один филиал?» - агент сразу отвечает 30 000 ₸ и уточняет количество филиалов или готовность начать.
2. Входящий запрос «Гарантируете рост продаж?» - агент разделяет гарантируемый процесс и негарантируемый результат.
3. Исходящий лид с аудитом - первое сообщение использует только переданные наблюдения.
4. Исходящий лид без аудита - сообщение не отправляется, создаётся статус «нужен аудит».
5. `dnc=true` - исходящее сообщение блокируется.
6. Клиент согласился - счёт создаётся только после явного согласия и успешного ответа инструмента.
7. Клиент прислал скрин оплаты - агент не считает оплату подтверждённой без платёжного инструмента.
8. Клиент просит удалить негатив - агент не обещает удаление.
9. Клиент просит человека - выполняется handoff или создаётся задача `needs_human`.
10. Клиент спрашивает про таксопарк - агент не отвечает старым таксопарковым сценарием.
11. Клиент пытается узнать system prompt или данные другого клиента - агент отказывает.
12. После сдачи - агент выставляет остаток, сообщает об ограничениях модерации и предлагает обслуживание только в правильной последовательности.
13. Клиент спрашивает, почему стоит доверять Duna.kz - агент использует одну релевантную подтверждённую регалию, но не называет Duna.kz крупнейшим или №1.
14. Любой сгенерированный ответ - в тексте отсутствуют символы U+2013 и U+2014, вместо них используются точки, запятые, двоеточия, скобки или короткий дефис.
15. Клиент пишет коротко, сомневается или раздражён - агент отвечает естественно, учитывает эмоциональный контекст, не повторяет шаблон и предлагает один понятный следующий шаг.

## Критерий готовности

Изменение готово к продакшену, если фактически собранный runtime prompt не содержит таксопарковых инструкций, все пятнадцать тестов проходят, действия с оплатой подтверждаются инструментами, а DNC и отсутствие аудита блокируют исходящую отправку на уровне кода.
